# Zero-Trust Ephemeral Pipeline Architecture (ZEPA)

> **A high-performance, fault-tolerant local bridge between volatile Web AI engines and dual-boot host operating systems.**

ZEPA is an automated, crash-proof file operations pipeline engineered to route, verify, and execute code and configuration payloads generated by cloud-based AI instances (`claude.ai`, `chatgpt`). It leverages a compiled **Rust asynchronous supervisor**, a **local 2B LLM model (`qwen2.5-coder:1.5b` via Ollama)** running on CPU/RAM for deep structural validation and recovery, and an isolated **Python sandboxed execution runtime**, all monitored live via a **Node.js dashboard UI**.

## 📋 Executive Overview

| Metric / Dimension | Specification / Implementation Detail | 
| ----- | ----- | 
| **Primary System Goal** | Zero-trust, crash-proof filesystem execution from un-sanitized external Web AI responses. | 
| **Core Supervisor** | Asynchronous Native **Rust** (Tokio runtime) process supervisor (**Thread X**). | 
| **Local Model Engine** | `qwen2.5-coder:1.5b` via **Ollama** running locally on **32GB DDR5 6000MHz RAM**. | 
| **Execution Sandbox** | Isolated **Python** worker (**Thread B**) enforcing `pathlib.Path.resolve()` boundaries. | 
| **Safety Architecture** | 3-Tier Security Gate (Tier 1: Rust Layout Scan, Tier 2: Python/2B LLM String Repair Gate, Tier 3: Pathlib Vault Lock). | 
| **Account Continuity** | Automated free-tier profile swapping via Postman CLI with recursive memory compression. | 
| **Log Management** | Dual-cap strategy: **100MB RAM** ring buffer for Node.js UI, **500MB Disk** ceiling with FIFO `.zip` rotation. | 
| **Host Portability** | Native dual-boot support (**Windows NTFS / Linux POSIX**) via kernel-level path abstractions. |

## 📊 Pre-Flight Telemetry Architecture

To optimize system resource allocation, the Postman script layer attaches two evaluation metrics to every payload header prior to local transmission:

### 1. Risk Score (Managed by Thread X Gatekeeper)

Based on structural complexity and potential formatting error risk (e.g., malformed JSON, trailing cutoffs, missing brackets):

* **Low Risk (Score 1-3):** Simple templates or basic config strings. If Thread X confirms no structural anomalies, it routes directly to Thread B.

* **High Risk (Score 4+):** Complex structures prone to nesting faults or truncation. If structural anomalies are detected, Thread X halts direct execution and routes the envelope to **Thread C** (Python String Engine) for deep research and formatting repair.

### 2. Code Score (Managed by Thread B / Thread C Environment)

Evaluates logical complexity, acting as a throttle for local 2B LLM processing:

* **Standard Pass:** If Tier 1 passes cleanly, Thread B processes the payload directly. If Python catches an execution exception, it restarts the local model instance and loops back (up to a max-retry limit of 3).

* **Deep Research & Repair Mode (Thread C Python Sandbox):** If Tier 1 flags structural errors, Thread X spawns Thread C. The Python worker uses advanced string parsing and the local `qwen2.5-coder:1.5b` model to repair and validate the code payload on 32GB DDR5 6000MHz RAM.

  * If validation succeeds, the repaired payload is forwarded to **Thread B**.

  * If verification fails, Thread C is destroyed, releasing RAM, and a soft error is sent to the **Node.js UI**.

## 🔄 End-to-End Operational Workflow Pipeline

1. **Generation:** Human prompt hits Web AI, returning a raw code/text payload.

2. **Telemetry Grading:** Postman Tests compute the `Risk Score` and `Code Score`, injecting them into the envelope headers.

3. **Relay:** Postman CLI posts the envelope to Thread A (Python ingest worker).

4. **Inspection:** Thread X inspects the payload against Tier 1 rules.

   * **If Clean:** Passes directly to **Thread B** for execution.

   * **If Structural Errors Detected:** Routes to **Thread C** (Python string repair worker).

5. **Thread C Sandbox Evaluation (If Triggered):**

   * **If Repaired / Validated:** Thread C passes the clean payload to **Thread B** and terminates.

   * **If Unrecoverable / Failed:** Thread X kills Thread C, frees memory, and pushes a soft error notification to the **Node.js UI**.

6. **Physical Write (Vault Lock):** Thread B verifies that the output target satisfies `is_relative_to(Path.cwd().resolve())` and commits the file to disk.

## 🔀 Free-Tier Account Rotation & Memory Pipeline

1. **Token Interception:** Postman scripts inspect Web AI response strings for usage limits (`"message limit reached"`, `"context full"`). When found, Postman appends `[STATUS: ERROR_LIMIT]`.

2. **Profile Swapping:** Thread X detects the error tag and updates Postman CLI parameters via environment flags (`-e Claude_Account_Work.json`), automatically shifting cookies and tokens to a fresh free-tier profile.

3. **Recursive Compression:** An asynchronous background routine routes multi-turn chat logs through a high-context window model (e.g., free ChatGPT) using a recursive summarization prompt to condense context across 2-3 iterations.

4. **Semantic Readme Snapshot:** Python executes a background task (`fastapi.BackgroundTasks`) that generates a 10-20 line Markdown overview of all files currently on disk.

5. **Hydration:** The snapshot is prepended to the compressed context block. When the new Claude profile starts, it reads this single block to restore project context with minimal token consumption.

## 📈 Logging Architecture & Storage Allocations

The logging pipeline employs a hybrid dual-tier memory and storage strategy designed to protect SSD health and prevent memory bloat:

```
[ Active System Logs ]
          │
          ├──> In-Memory Ring Buffer (RAM Cap: 100MB)  ──> Pushed to Node.js UI
          │
          └──> Flushed to Disk Active Dir (Disk Cap: 500MB)
                     │
                     └──> (When > 500MB) ──> Compress Old Logs (.zip) ──> FIFO Archive Purge

```

* **RAM Memory Limit (100MB Cap):** Active terminal stdout/stderr streams maintain an in-memory ring buffer capped at **100MB**. This feeds the Node.js dashboard real-time data without leaking system memory.

* **Disk Ceiling Limit (500MB Cap):** Critical logs, stack traces, and execution records flush to disk up to a total storage limit of **500MB**.

* **Log Rotation & Archiving:** When active disk logs exceed 500MB, the system automatically rolls active log files, compresses them into timestamped `.zip` archives inside `logs/archives/`, and clears the oldest archives using a FIFO (First-In, First-Out) policy.

## 💻 Cross-Platform Portability (Dual-Boot Setup)

ZEPA runs natively across both **Windows (NTFS)** and **Linux (POSIX)** partitions without hardcoded path conditionals:

* **Path Abstraction:** Rust (`std::path::PathBuf`) and Python (`pathlib.Path`) treat paths as dynamic abstractions rather than string literals.

* **Kernel Normalization:** Path joins using the `/` operator evaluate against the host OS kernel at runtime. Unix paths use forward slashes (`/`), while Windows builds automatically convert separators to native backslashes (`\`) with drive root support (`C:\`).

## 🛠️ Fault Containment & Recovery Matrix

| Failure Event | Component Affected | Supervisor Action | System Recovery State | 
| ----- | ----- | ----- | ----- | 
| **Malformed JSON / Structural Cutoff** | Thread X Gatekeeper | Routes payload to Thread C (Python) for repair instead of directly to Thread B. | **Contained.** Thread C attempts recovery via Python string logic & 2B LLM. | 
| **Unrecoverable Thread C Repair** | Thread C (Python / Ollama) | Thread X terminates Thread C; releases RAM and sends soft error to Node.js UI. | **Safe.** Thread B remains undisturbed; dashboard alerted. | 
| **Path Traversal Escape (`../`)** | Thread B (Python) | `is_relative_to()` triggers `PermissionError`. Process halts file write. | **Protected.** File system locked; Tier 3 violation alert pushed to UI. | 
| **Python Process Panic** | Thread B Engine | Thread X detects non-zero exit code via process monitor. | **Recovered.** Respawns Thread B worker within 3 seconds (Max 3 retries). |
